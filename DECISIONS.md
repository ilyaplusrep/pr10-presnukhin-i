# DECISIONS.md

## Вариант

- Номер варианта: 16.
- Часть А: добавлен тип `POSTAL` в `DeliveryType`, класс `PostalPolicy implements DeliveryPolicy`
  (supports: `type == POSTAL && weightKg <= 2`, cost: `max(300, distanceKm * 20)`) и ветка
  `case POSTAL -> new PostalPolicy()` в `DeliveryPolicyFactory.get`. Существующие политики и
  метод `DeliveryService.calculate` не изменены.
- Часть Б: `DeliveryService.addPostalCost(DeliveryService service, DeliveryRequest req)` → `double`:
  создаёт копию запроса с типом POSTAL и вызывает `service.calculate`. Если почта не берёт
  посылку (вес > 2 кг), исключение из `calculate` пробрасывается как есть.

## Решение 1. POSTAL добавлен ровно тремя шагами OCP, без правки calculate

**Что решено.** Изменения варианта — новое значение enum, новый класс и одна строка в фабрике.
Ограничение веса и формула живут только в `PostalPolicy`, константы вынесены в поля
`MAX_WEIGHT_KG`, `MIN_COST`, `COST_PER_KM` (как и в двух других платных политиках).

**Альтернатива.** Добавить в `DeliveryService.calculate` ветку `if (type == POSTAL)` или
сделать `PostalPolicy` наследником `StandardCourierPolicy`, раз формулы похожи
(`max(min, км × тариф)`).

**Почему так.** Ветка в сервисе нарушила бы R8 и вернула бы ту самую условную логику,
которую работа убирает. Наследование связало бы почту с курьером: изменение минимума
у курьера (вариант 5) молча изменило бы и почту. Switch по enum без `default` даёт ещё одну
гарантию: если добавить значение в enum и забыть `case`, проект не скомпилируется. Это
проверено на практике: после добавления `POSTAL` в enum javac потребовал новую ветку.

## Решение 2. DeliveryRequest проверяет физическую корректность, но компоненты не менялись

**Что решено.** В record добавлен компактный конструктор: `type != null`, а `distanceKm`,
`weightKg`, `orderAmount` — конечные числа не меньше 0. Компоненты и accessor-ы те же.
`addPostalCost` сделан `static`, как в сигнатуре варианта (сервис передаётся параметром).

**Альтернатива.** Оставить record без проверок и ловить отрицательные значения в каждой
политике или в SelfCheck.

**Почему так.** Без проверки `DeliveryRequest(STANDARD, -100, 1, 0)` даёт стоимость 500 —
`Math.max` маскирует ошибку, и неверный ввод становится «правильной» ценой. Проверка в
одном конструкторе защищает все политики сразу, включая будущие, и не требует правки ни
одной из них. Нулевые значения разрешены: строка `STANDARD;0;0;0` из методички должна
давать 500. Ограничения конкретного способа (вес ≤ 20, ≤ 10, ≤ 2) остаются в `supports`,
потому что это правила политики, а не корректность запроса.

## Ответы на контрольные вопросы

### Вопрос 1. Какой принцип ООП или паттерн обеспечивает наибольшую гибкость при добавлении нового типа доставки и где он реализован?

Open/Closed Principle, реализованный связкой Strategy + Factory. Strategy — интерфейс
`DeliveryPolicy` и его реализации `StandardCourierPolicy`, `ExpressPolicy`, `PickupPolicy`,
`PostalPolicy`; каждая хранит свою формулу и своё ограничение. Factory —
`DeliveryPolicyFactory.get`, единственное место, где тип связывается с классом. Контекст —
`DeliveryService.calculate`, который знает только интерфейс. В варианте 16 это проверено на
деле: POSTAL добавлен новым классом, значением enum и одной строкой `case` в фабрике, а
файлы StandardCourierPolicy, ExpressPolicy, PickupPolicy и метод calculate не открывались.
Все 18 базовых проверок SelfCheck после этого прошли без изменения ожиданий — значит,
расширение не сломало существующее поведение.

### Вопрос 2. Какой класс содержит ключевую логику выбора стратегии и почему вы разместили её именно там?

Логика выбора — в `DeliveryPolicyFactory.get(DeliveryType)`: switch expression по enum, каждая
ветка только создаёт объект (`new PostalPolicy()`), формул нет (R4). Выбор вынесен из
сервиса, чтобы у класса была одна причина для изменения (Single Responsibility): сервис
меняется, если меняется порядок «выбрать → проверить → посчитать», фабрика — если меняется
набор способов доставки, политика — если меняется тариф. При добавлении POSTAL правка
коснулась только фабрики, а не всех мест, где нужна политика. Switch без `default` выбран
сознательно: компилятор проверяет полноту, и пропущенный тип — ошибка сборки, а не
`null` во время работы. Проверку `type == null` я оставил в фабрике явной, чтобы получить
IllegalArgumentException вместо NullPointerException из switch.

### Вопрос 3. Как Activity-диаграмма отражает один конкретный участок вашего кода?

Узел A1 «Получить политику доставки через Factory по типу запроса» соответствует строке 13
DeliveryService.java: `DeliveryPolicy p = factory.get(r.type());`. Предыдущий узел
«Определить тип доставки» — это выражение `r.type()` в той же строке, accessor record-а.
После A1 на диаграмме нет разветвления по типам: следующий узел «Проверить возможность
доставки полиморфно» — строка 14 `if (!p.supports(r))`, а ромб «Доставка возможна?» с веткой
«нет» к IllegalArgumentException — строки 14–15. Ветка «да» ведёт к узлу «Рассчитать
стоимость полиморфно», это строка 16 `return p.calculateCost(r);`. Для POSTAL, 30 км, 1.5 кг
путь такой: начало → параметры → тип POSTAL → A1 (PostalPolicy) → supports = true → «да» →
600.0 → завершение. Для POSTAL 3 кг: … → supports = false → «нет» → исключение.

### Вопрос 4. Какое изменение требования должно затронуть минимальное количество классов и почему?

Изменение тарифа или лимита одной политики, например «лимит веса STANDARD 15 вместо 20».
Затрагивается один класс — `StandardCourierPolicy`, одна константа `MAX_WEIGHT_KG`, которую
читает только её `supports`. Фабрика, сервис, другие политики, enum и record не меняются:
формула и проверка инкапсулированы внутри класса-политики, а остальной код видит его только
через интерфейс. Для почты то же самое: «почта до 5 кг» — одна строка в `PostalPolicy`.
После правки нужно обновить лишь ожидания граничных проверок в SelfCheck и sample.csv
(вес 20 → 15/16), а запуск SelfCheck покажет затронутые кейсы. Activity-диаграмма при этом
не меняется вовсе, потому что она описывает алгоритм сервиса, а не формулы политик.

## Фрагмент кода для анализа

```java
if (type == EXPRESS) { ... } else if (type == STANDARD) { ... } else if (type == PICKUP) { ... }
```

Ошибка: условная логика вместо полиморфизма — один метод содержит все алгоритмы расчёта и
все ограничения, что нарушает Single Responsibility Principle. Причина проблемы — нарушение
Open/Closed Principle: для варианта 16 (POSTAL) пришлось бы открыть этот метод и дописать
ещё одну ветку, рискуя сломать соседние; к тому же пропущенная ветка не заметна компилятору
и тихо даёт неверный результат. Исправление в проекте: интерфейс `DeliveryPolicy`, по
классу на способ доставки, `DeliveryPolicyFactory` со switch по enum без `default` и вызов
`policy.calculateCost(req)` в `DeliveryService`. Связь с правилами: R2 — расчёт не зависит
от названия способа после выбора стратегии; R8 — в `calculate` нет if-else по типам, только
`factory.get` и полиморфные `supports`/`calculateCost`; R9 — POSTAL добавлен без правки
существующих политик и сервиса.
